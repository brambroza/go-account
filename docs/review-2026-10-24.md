## Sprint B — ฟีเจอร์บัญชีที่ MVP ต้องมี (หน้าเว็บ)

**ต้องตัดสินใจกติกาธุรกิจก่อน (ใช้ /change-request ถ้ามี spec ลูกค้าแล้ว):**
- B1 (Critical) ใบลดหนี้หลังรับเงิน — กฎหมาย (ม.86/10, ม.82/10) ต้องออกได้ แต่โค้ดจำกัดไว้ที่ยอดค้าง (`actions.ts:155-160`) เสนอ: จำกัดที่ยอดใบกำกับ − ลดหนี้ก่อนหน้า ส่วนเกินตั้งเจ้าหนี้ลูกค้า/บันทึกคืนเงิน
- B2 (High) flow งานบริการ: ใบแจ้งหนี้ → ใบเสร็จ/ใบกำกับภาษีตอนรับเงิน (ม.78/1)

**งานบัญชี/ภาษี:**
- B3 ภาษีซื้อ: `supplierInvoiceDate` + งวดใช้สิทธิภายใน 6 เดือน (ม.82/3), ตรวจเลขผู้เสียภาษี/สาขาผู้ขาย (ม.82/5) — เลิกแนะนำให้แก้วันที่เอกสารใน UI
- B4 ใบลดหนี้แสดงมูลค่าเดิม/ที่ถูกต้อง/ผลต่าง/VAT ผลต่าง (ม.86/10) ทั้งพิมพ์และ XML; ใบเพิ่มหนี้ (ม.86/9)
- B5 งบฐานะการเงิน + ปิดปีโอนกำไรสะสม + ยอดยกมา (ย้ายจาก Express)
- B6 ภ.พ.30 ยกยอดภาษีชำระเกิน + รายการปิดบัญชี VAT
- B7 หัก ณ ที่จ่ายระดับบรรทัด (สินค้าไม่หัก), เตือนเมื่อจ่ายต่ำกว่า 1,000 บาท, แบ่งจ่ายหลายครั้ง, พิมพ์หนังสือรับรอง 50 ทวิ
- B8 หน้า detail ฝั่งซื้อ + ใบลดหนี้ผู้ขาย
- B9 ธนาคารหลายบัญชี + กระทบยอด, เงินสดย่อย, ใบเสนอราคา

**UX คีย์เร็วแบบ Express:**
- B10 Autocomplete ลูกค้า/ผู้ขาย + เพิ่มใหม่จากฟอร์ม, Enter เพิ่มแถวแล้ว focus, DatePicker พ.ศ. ตัวเดียวทั้งระบบ (dialog ยังใช้ native date), จำเรท WHT ล่าสุดของลูกค้า
- B11 รหัสผู้ติดต่อถัดไปจากค่าสูงสุด ไม่ใช่ `length+1`; Ctrl+K ค้นเอกสารซื้อ
- B12 Bundle: `manualChunks`, ถอด locale DataGrid ที่ไม่ใช้, lazy `SettingsDrawer` (index.js ตอนนี้ 917 kB)

## Phase C — Backend (ต้องให้ Technical Lead เคาะ)

- **Stack:** architect เสนอ Node/Fastify + TS + PostgreSQL RLS (org default) แทน .NET ใน README เพราะใช้ `src/domain` ร่วมกันได้เป็น package `@go-account/core` ตัวเลขสองฝั่งตรงกันแน่นอน; ถ้าต้องการ .NET ให้จำกัดอยู่ที่ signing service
- เตรียมฝั่งหน้าเว็บ: `run(): Promise<R>`, แยก `AccountingRepository` (local/api), inject `clock`/`idGen`/`numberAllocator` เข้า action
- เลขเอกสารใน DB transaction (`doc_sequence ... FOR UPDATE`), Idempotency-Key, RLS ต่อ tenant + test ข้าม tenant, auth + role, audit log append-only, ปิดงวดบังคับที่เซิร์ฟเวอร์, เก็บข้อมูล 5–7 ปี, PDPA
